# S005 · `PScrollArea`, wrapping Reka UI's `ScrollArea`

**Status:** ✅ COMPLETE.
**Depends on:** [S002](S002-2026-08-28-pmenu-reka-dropdown.md), which brought Reka UI in.
**Consumer:** rp-engine's `SessionTranscript.vue` and `TurnComposer.vue`, in that repo's own
follow-up to S034.
**Origin:** rp-engine wanted a subtle scrollbar — track and thumb only, no native end
buttons — shared by the session transcript's scroll well and the composer's auto-growing
text field. `::-webkit-scrollbar` has no Firefox equivalent and cannot draw just a track and
thumb on every OS, which is what sent this to Reka's `ScrollArea` instead of hand-rolled CSS.

## Scope

- [x] `PScrollArea` over Reka's `ScrollAreaRoot` / `Viewport` / `Scrollbar` / `Thumb` /
      `Corner`. Styled with existing tokens only (`hairline`, `hairline-soft`) — no new
      token.
- [x] The root owns no height, the same way `PPanel` owns no padding: pass a sizing class.
      `viewport-class` is separate, so content padding does not land on the root and push the
      scrollbar off to the side.
- [x] `visible` prop, boolean, default `true`. `true` uses Reka's own `type="hover"`:
      nothing is in the DOM until the pointer enters the area or it scrolls, then a track and
      thumb fade in over 150ms and fade back out. `false` renders no scrollbar at all, ever —
      the area still scrolls. **Decided over two other shapes mid-build**, both rejected by
      the consumer's product owner: a `type` prop overloading Reka's five-way enum with an
      extra `"hidden"` value (leaked an internal API onto a binary decision), and a numeric
      `opacity` prop for a mouse-proximity fade (would have pushed distance-tracking logic
      into rp-engine for a requirement that turned out to already be satisfied — Reka's own
      hover fade is already smooth, no proximity math needed).
- [x] Tests (vitest-browser-vue, real Chromium): slot content renders; the scrollbar is
      absent until pointer-enter, then appears; `visible: false` never renders one even while
      hovered; `visible: false` still scrolls via `scrollTop`.
- [x] Exposes the real scrolling element as `viewport` (re-exposes Reka's own
      `ScrollAreaRoot.viewport`, via a getter rather than a `computed` — `defineExpose` does
      not unwrap a nested `computed`, but Vue's public-instance proxy does auto-unwrap a
      top-level ref, so a getter reading through `rootRef.value.viewport` needs no `.value`
      of its own).
- [x] Attrs split by hand between the two DOM nodes this component actually has:
      `inheritAttrs: false`, `class`/`style` (sizing) bound onto the root, everything else
      (`data-testid`, `aria-*`) onto the viewport — the root's own `scrollHeight` never
      exceeds its `clientHeight` (its child is `h-full`), so only the viewport is ever really
      the thing overflowing. Found wiring rp-engine's transcript, whose layout regression
      test needed `data-testid="transcript-scroll"` on the element actually proven to scroll.
- [x] **Documented and regression-tested the sharpest edge a caller will hit:** the root
      needs an explicit pixel `height`, not `max-height`, to actually scroll. The viewport is
      `height: 100%` of the root, and a percentage height resolves against an
      *indeterminate* containing block (`max-height` alone) as `auto` — the viewport just
      grows past the cap instead of clipping, and Reka never sees an overflow to track. Found
      wiring rp-engine's composer, where the field's height clamp had to move from its own
      inline style onto this component, computed as an explicit pixel value.
- [x] A story with both variants (`visible: true` default, `visible: false`), plus docs.
      Confirmed in Histoire itself, not just by convention: `histoire build` picks up
      `*.story.vue` automatically (`storyMatch` glob in `histoire.config.ts`), no separate
      registration step — 9 stories, 24 variants total with this one included.
- [x] 50/50 tests, typecheck, build clean across four commits. `dist/index.js` carries the
      Tailwind class strings intact (`bg-hairline-soft`, `w-2 p-0.5`, `touch-none` all
      verified present).

## Note for whoever adopts this next

Reka's `ScrollAreaViewport` already hides the *native* scrollbar cross-browser on its own
(`[data-reka-scroll-area-viewport] { scrollbar-width: none; ... }`), which is what makes
"only a track and a thumb, nothing else" true regardless of OS or browser — this component
does not add that part, Reka already had it.

**The one thing to get right on every new usage: give the root a real `height`.** See the
component's own doc comment and the story's docs block for the full reasoning — a
`max-height` class looks correct, clips visually, and silently does not scroll.
